写并发代码的人，几乎都被这三个词绊过：**进程、线程、协程**。面试官爱问，文档里混用，一线工程师在不同语境下说出的"线程"含义往往都不一样。这篇文章试图把它们的本质差异说清楚，并给出一些选型直觉。

## 一句话总结

> **进程是资源分配的最小单位，线程是 CPU 调度的最小单位，协程是用户态调度的最小单位。**

听起来像绕口令，下面我们一层层拆开。

## 三个概念的对照

| 维度 | 进程 (Process) | 线程 (Thread) | 协程 (Goroutine/async) |
|---|---|---|---|
| 由谁创建 | 内核 | 内核（通常通过 pthread） | 用户态运行时 |
| 调度方 | 内核 | 内核 | 程序自己 |
| 切换开销 | 最高（页表、上下文） | 中等（寄存器、栈） | 最低（几百字节栈 + 寄存器） |
| 内存隔离 | 完全独立 | 共享进程地址空间 | 共享线程地址空间 |
| 数量级 | 几十到几百 | 几百到几千 | 几万到几百万 |
| 通信方式 | 管道、socket、信号 | 共享内存、锁 | channel、async/await |

## 进程：资源的"房子"

进程是操作系统分配资源的最小单位。每一个进程在内核眼里是一份独立的"房子"：有自己的页表、有自己的文件描述符、有自己的信号处理表。从一个进程切换到另一个，CPU 要换页表基址、刷 TLB，代价很大。

但在用户眼里，进程的好处是**强隔离**。一个进程崩溃通常不会带崩另一个。所以浏览器把每个 Tab 做成进程，IDE 把语言服务做成单独的进程。

## 线程：CPU 眼中的"任务"

线程保留了进程的大部分资源（地址空间、打开的文件），但**调度粒度更细**。内核调度器看的是线程而不是进程。在同一个进程内，线程切换不需要换页表，开销比进程低一个量级。

代价是**共享带来的复杂度**。两个线程同时改一个变量，必须加锁；锁用错了就是死锁、活锁、优先级反转。Java 里那一堆 `synchronized`、`ReentrantLock`、`AQS`，本质上都是在解决"同一进程内多线程共享内存"的难题。

## 协程：用户态的"假线程"

协程的革命性在于：**调度权从内核拿回了用户态**。

线程一旦 `new` 出来，内核随时可能抢走 CPU。但协程什么时候让出执行权，由程序自己决定。Go 的 `go func()`、Kotlin 的 `launch{}`、Python 的 `async def` 都是协程。

让我们看一个最简的 Go 示例：

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	go say("world") // 启动一个协程
	say("hello")    // 主协程
}

func say(s string) {
	for i := 0; i < 3; i++ {
		fmt.Println(s)
		time.Sleep(100 * time.Millisecond)
	}
}
```

输出大致是：

```
hello
world
hello
world
hello
world
```

`go say("world")` 在用户态创建了一个协程，运行时把它放到 GMP 调度器的本地队列。`time.Sleep` 触发的是**协程让出**，而不是线程阻塞——内核完全不知道发生了什么。

## 怎么选？

实践中我常用这样的判断顺序：

1. **需要强隔离？** → 用进程（容器、虚拟机）
2. **CPU 密集、需要榨干多核？** → 用线程 + 线程池
3. **I/O 密集、高并发连接？** → 用协程（Go、Rust async、Java virtual thread）

Go 之所以在云原生时代流行，正是因为它把协程做成了语言一等公民，写高并发服务的门槛被大幅降低。Rust 通过 `tokio` 走的是另一条路——零成本抽象 + 显式生命周期，性能更极致但学习曲线更陡。

## 一句话记住

- **进程**管资源
- **线程**管 CPU
- **协程**管"我什么时候该让别人跑"
